# Architecture

The single package is a Bun stdio executable. `src/cli.ts` handles arguments, explicit local fingerprint/init commands, trusted submission configuration and the SDK transport. `src/server.ts` registers five tools through their adapters: `get_balance`, `list_tasks`, `get_task_status`, `get_task_report`, and `create_indexing_task`. No submission flags leaves writes disabled, with pure previews available.

`src/client.ts` sends one GET per account or task-list call and one POST per task-status or task-report call. It builds routes from fixed endpoints and validated inputs. `list_tasks` reads one explicit zero-based page and never traverses pages automatically. `get_task_status` selects one fixed status route from six supported families and sends either one `task_id` or a `task_ids` array. `get_task_report` selects one fixed report route from six families and sends one opaque `task_id`; generic reports are unpaginated, while backlink reports send exactly one page with explicit page and limit values. Neither tool splits or retries requests, follows up, or requests another family. The injectable fetch function supports isolated tests; the production CLI provides no endpoint override. The raw API key goes only in the Authorization header. Redirects and automatic retries are disabled. A per-call abort controller enforces the 10-second deadline, combined with the SDK request cancellation signal. Timers are cleared after settlement.

The shared reader enforces this MCP's compiled-in 16 MiB ceiling on decoded response-body bytes before JSON decoding. This is a local safety bound, not a SpeedyIndex maximum or a hard process-RSS claim; unusually large pages and reports are rejected.

The account envelope has numeric `code: 0` and all three required balance fields. Zod validates finite nonnegative numbers, strips unknown fields, and validates the public output with its observation timestamp. A task-list envelope must have `code: 0`, safe nonnegative integer page fields, and at most 1,000 task rows; its echoed page must match the request. Empty pages beyond `last_page` are allowed, while non-empty results beyond that inclusive final page are rejected. Every task has a nonblank opaque ID. Other documented summary fields are optional, validated when present, mapped to camelCase, and unknown fields are stripped. The public list output omits unavailable optional values.

Task status input uses one of six family values and exactly one ID form. Batch IDs must be unique and nonblank; the client uses unique IDs for exact correlation, and the provider documents a 1,000-ID maximum. A status response may contain one task or an array for either input form. The client validates known root and direct-child fields, strips unknown fields, maps names to camelCase, and correlates records by exact root ID. It returns tasks and omitted IDs in request order. `unreturnedIds` describes omissions in one response and does not establish that a task is missing. Optional fields remain omitted when absent. Counts and day values must be safe nonnegative integers; token charges and refunds must be finite nonnegative numbers. Status strings and explicit completion booleans pass through; the client does not infer completion from counts or status text. The optional `dripFeed` and `awaitingResult` flags are observed provider fields, not universal guarantees. Direct children carry common task/PPI fields and optional `day`, with no nested children.

If a known field on any returned task or direct child has the wrong type, the entire task-status call fails with no partial `tasks`; `unreturnedIds` reports omissions only from an otherwise valid response.

Task reports have a separate `src/task-report.ts` schema and normalizer. Generic report results require the documented core fields and preserve URL strings and array order exactly; optional known metadata is validated when present and unknown result-root fields are stripped. Provider IDs correlate exactly to the requested ID and appear publicly as `taskId` only. Backlink reports validate one page, its exact page/ID correlation, the requested donor limit, and opaque donor rows as finite JSON objects; nested donor keys and values are preserved. A wrong type or explicit `null` for a known field, or a donor row that is not an object, fails the whole call. Nested JSON null values inside valid donor objects remain allowed and are preserved. Empty pages beyond `lastPage` are valid, but nonempty pages beyond it are rejected. Report fields and counts do not establish completion, retry permission, or fresh Google indexing truth.

The four read tools return structured content and equivalent JSON text on success. Their errors use fixed messages without structured results, provider bodies or thrown error details. The submission adapter validates its own structured success and error results, including identical JSON text; SDK 2.3.1 skips output validation for `isError: true`. SDK input validation occurs before the handler, so those input failures need not have application structured content.

The SDK stdio transport handles stdin EOF, closes the connection, and aborts in-flight requests. Startup and previews open no ledger. Only an enabled submit opens existing state; only the explicit local init command creates state. CodeGraph is an optional developer tool, independent of the runtime and build. The executable starts no web listener, scheduler or deployment service.

## Guarded indexing submissions

`src/create-indexing-task.ts` owns strict public schemas, frozen provider bodies, quotes, fingerprints and root ACK normalization. `src/submission-policy.ts` loads an explicit bounded private JSON policy once and derives trusted key/UTC context. `src/submission-host.ts` coordinates that snapshot with the unchanged V1 ledger and a private paid transport. The read-only provider client has no submission method. The thin tool adapter forwards SDK cancellation and validates application output; it does not accept policy authority through MCP arguments.

Google submits always request Pay-Per-Result with explicit `drip_feed: false` or valid drip days. Yandex omits Google-only fields. The host serializes the validated body once, preserving title and ordered URL text, and hashes those exact UTF-8 bytes. It rejects overflow before preparation: 10,000 URLs, 8,192 bytes per URL, 1,024 bytes per title and 2,097,152 bytes per serialized body are inclusive limits. Google drip days are 2 to 30 and at most the URL count. Unsupported families, authority overrides, duplicate URLs and malformed Unicode fail validation without normalization or truncation. URLs are never fetched.

For N URLs, the independent maximum-exposure estimate is Google `100*N` tokens, or Yandex `20*N` tokens plus N indexer credits; checker exposure is zero. Yandex consumes credits first, so booking both independent maxima is conservative against outside credit use. The host does not read balances or net refunds against its reservation. Quote identity binds version, family, fixed route, exact body digest, URL count and three-unit exposure. It excludes key, policy and day so an unchanged payload keeps its quote across midnight.

The trusted policy has explicit enabled/mode/revision/scope/expected-key fields, finite safe-integer token/indexer/checker caps, and a UTC-day period kind. The loader requires a canonical absolute file, effective-UID ownership, mode `0600`, one hard link, no symlink, trusted ancestors and at most 16,384 bytes. It uses a no-follow descriptor with bounded reading and identity checks; it does not repair or discover files. The state path remains a syntactic reference until submit. The trimmed visible-ASCII effective key is bounded at 8,192 bytes; its domain-separated SHA-256 must match the policy's expected fingerprint. A key fingerprint does not establish provider account identity. Raw keys, expected fingerprints and raw policy never enter tool results or logs.

The canonical policy digest includes caps and expected key but excludes the current day. Host clock time determines `utc-day:YYYY-MM-DD` and UTC midnight boundaries. Caller acknowledgement mode requires both current quote and authorization digests for a new intent; operator policy mode permits new submits without an acknowledgement, but validates both digests if supplied. The authorization digest binds quote, policy, key, scope and day. This echo detects stale context and supplies no human authentication, one-use permission or request-ID binding. Operators control host access and restart all cooperating hosts to apply policy changes; no reload loop exists. Incomplete/invalid configuration disables writes while preserving stdio/read availability.

The host performs these separate steps with no SQLite transaction spanning an await or network operation:

1. Validate and freeze the request. Return preview without key/state/network requirements. For submit, check trusted policy/key/context and cancellation, then open existing V1 state.
2. Let real `prepareIntent` compare an existing request ID for exact replay. Return durable state without another capability, reservation or POST. For new IDs, allow only one new in-flight submit per process, validate acknowledgement and prepare durably. Cross-process coordination uses the shared ledger.
3. Yield through a timer and an immediate to an actual I/O turn after prepare, allowing queued stdio cancellation. If cancelled, use the prepared version-zero CAS to cancel and release holds only after commit. A lost CAS requires a fresh read.
4. Claim once with the creator capability. Only the winning version-one claim receives an outcome token. Yield to another actual I/O turn, then perform final signal/body/header checks. A proven no-fetch failure after claim records rejected with a `not_sent` observation; V1 cannot cancel a dispatching intent.
5. Mark the attempt immediately before one HTTPS POST to `https://api.speedyindex.com` and the fixed Google or Yandex `/v2/task/.../indexer/create` route. Send the frozen JSON, raw trimmed Authorization key, JSON Content-Type/Accept and package User-Agent. Reject redirects and use a 10,000 ms deadline through response-body reading. Do not retry, split, fall back or poll.
6. Read at most 65,536 response bytes before fatal UTF-8 and JSON decoding, independent of Content-Length. Record one accepted/rejected/unknown outcome even after caller cancellation, then close the ledger and release the guard.

Only HTTP 200 with root numeric `code: 0`, a valid opaque root `task_id` and exact root family establishes an accepted ACK. Optional PPR/drip echoes must match; omitted echoes are allowed. Local task-ID limits are 4,096 UTF-8 bytes, valid Unicode, nonblank and no C0/DEL controls, with accepted text preserved. Root codes 1 or 2 without any task-ID field on HTTP 200/401/402/413 establish rejection. Other post-invocation failures, including malformed/nested ACKs, redirects, resets, deadlines and aborts, remain unknown. The read tools retain their separate 16 MiB body limit.

A fully parsed valid ACK can record accepted despite a later abort. If outcome persistence fails, the host rereads once and returns only confirmed durable state. A held dispatching result separates the safe ACK observation as `recorded: false` with `OutcomePersistenceFailed`; an unavailable reread reports `StateUnavailable` with last-observed dispatching rather than asserting current durability. HTTP alone cannot return durable accepted success. Cancellation may suppress the SDK response while durable state remains the recovery reference.

## Local V1 ledger and limits

`src/submission-ledger.ts` records immutable request identity, exact submitted URL strings, three independent unit reservations, and prepared, dispatching and terminal outcomes. It stores no key, title, raw provider body, provider error or plaintext capability. The host supplies scope, period, caps, policy digests and quote data from trusted configuration; this repository chooses no operator values. For each credential and budget scope, period IDs and start times map one-to-one. A new reservation may reuse the latest mapping or create a period whose start is strictly later than every recorded start; aliases and earlier contexts fail with `StalePeriodContext`.

For an existing credential and request ID, replay comparison checks budget scope, policy revision and digest, task family and route, payload digest, quote version and fingerprint, reservation values, and the ordered exact URL strings. Period ID, period start and direct cap values are excluded from V1 replay identity; the host policy digest nevertheless binds cap changes to policy identity. An exact replay returns the stored intent and its original period without another reservation or current-period acknowledgement. Other immutable mismatches return `RequestIdConflict`. New reservations use trusted current caps; policy revisions do not reset retained exposure. Prepared/dispatching/unknown reservations count across all periods, and accepted reservations count for their original reservation day. Rejected/cancelled rows count zero. Exposure sums grow with retained history. Unresolved exact URL holds span scopes for that key; accepted rows release URL holds, allowing a deliberate new ID to submit again.

`initializeLedger` creates only a new private local directory and database. Both entry points require a canonical absolute POSIX path. The parent of a new state directory must already exist, and each ancestor must be a non-symlink directory owned by root or the current UID and not writable by group or others; root-owned sticky temporary directories are permitted. The final state directory must be owned by the current UID with mode `0700`. The database and any sidecars must be regular files owned by the current UID with mode `0600`. Callers may resolve operating-system path aliases before calling; the module does not follow aliases.

A failed initialization may leave a directory, partial database or sidecars, or even a complete version-one database if a later validation fails. It does not automatically remove or retry that path. Inspect any artifacts before recovery and never replace state to bypass held reservations. Normal `openLedger` validates paths/files, opens without CREATE, verifies the complete V1 schema, then configures WAL/foreign keys/FULL/busy timeout. WAL configuration can change persistent journal mode and create sidecars after verification. SQLite opening and reads can also touch existing SHM bookkeeping before a wrong-version rejection; these bookkeeping effects are distinct from application bootstrap or repair. Open does not bootstrap, repair, reset, rebuild or replace records. Unresolved prepared/dispatching/unknown state stays held across reopen, without lease expiry, resend or automatic release.

Bun SQLite operations are synchronous. The 2,000 ms busy timeout controls lock waiting, not total latency; retained-history sums, inserts and other operations add work. SQL can block stdio parsing, reads, pings, cancellation delivery and timer callbacks. Verified pre- and post-claim I/O turns allow queued cancellation at those boundaries; they cannot interrupt SQL already running or atomically cancel a remote request. The HTTP 10-second deadline is not a whole-tool deadline. Actual SDK queued-cancellation tests cover both busy failure and successful prepare; a separate process test covers queued I/O after a winning claim.

SQLite transactions coordinate cooperating processes that open the same local database. They do not reserve SpeedyIndex wallet funds, identify an account, coordinate database copies or hosts, prevent other clients spending the same wallet, or guarantee that distinct submissions cannot create duplicate jobs. WAL with SQLite `synchronous=FULL` stays subject to the VFS, filesystem, storage hardware, and operating system; it is not a power-loss guarantee.

V1 records standalone intents without parent/campaign lineage. Titles, URL equality and request IDs cannot infer relationships. A future additive V2 design must retain V1 records, holds, events and dispatch ownership, add explicit immutable relations atomically with new preparations, and leave unattributed legacy rows unknown. It needs a separately verified offline migration with all hosts quiesced and a coherent backup; normal startup/open must never migrate or recreate state. No lineage table, migration command or retry mechanism ships here.

The provider contract comes from the [official API reference](https://en.speedyindex.com/api.php) and the [account API page](https://app.speedyindex.com/cabinet/api). This integration is unofficial. Future tools need their own scope, action boundaries, documentation, and verification; see the [roadmap](implementation-plan.md).
