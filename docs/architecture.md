# Architecture

The single package is a Bun stdio executable. `src/cli.ts` handles arguments, explicit local fingerprint/init/migration commands, trusted submission configuration and the SDK transport. On this source branch, `src/server.ts` registers nine tools through their adapters: `get_balance`, `list_tasks`, `get_task_status`, `get_task_report`, `create_indexing_task`, `create_index_check`, `create_backlink_check`, `plan_retry`, and `get_retry_history`. No submission flags leaves writes disabled, with pure previews available. Branch implementation does not establish a release or provider activation.

`src/client.ts` sends one GET per account or task-list call and one POST per task-status or task-report call. It builds routes from fixed endpoints and validated inputs. `list_tasks` reads one explicit zero-based page and never traverses pages automatically. `get_task_status` selects one fixed status route from six supported families and sends either one `task_id` or a `task_ids` array. `get_task_report` selects one fixed report route from six families and sends one opaque `task_id`; generic reports are unpaginated, while backlink reports send exactly one page with explicit page and limit values. Neither tool splits or retries requests, follows up, or requests another family. The injectable fetch function supports isolated tests; the production CLI provides no endpoint override. The raw API key goes only in the Authorization header. Redirects and automatic retries are disabled. A per-call abort controller enforces the 10-second deadline, combined with the SDK request cancellation signal. Timers are cleared after settlement.

The shared reader enforces this MCP's compiled-in 16 MiB ceiling on decoded response-body bytes before JSON decoding. This is a local safety bound, not a SpeedyIndex maximum or a hard process-RSS claim; unusually large pages and reports are rejected.

Internal callers can opt the three task-read methods into `src/read-budget.ts` with one trusted budget and explicit monotonic start. The budget permits at most 64 entered fetches and 32 MiB of aggregate decoded chunks over a 60-second horizon. Failed and repeated calls keep their charges. It charges each delivered chunk before copying, decoding or observing cancellation; overflow terminates the read. A completed last attempt or exact byte total can succeed, while the next admission fails. Trusted constructor limits can only lower these bounds. The constructor captures clock/timer functions and receivers once; no MCP, environment, policy or CLI selector exposes them. Each request uses the smallest of the finite positive client timeout, 10 seconds, a lowered request ceiling and remaining horizon. Fresh checkpoints reject stale results after parsing and normalization, without promising to interrupt synchronous CPU work.

Each budget admits one active read without queuing. The client freezes its first classified failure before cleanup; current cancellation precedes horizon expiry, request timeout, aggregate overflow and ordinary transport/response failures. A later abort or cleanup rejection cannot replace that cause. The client awaits actual fetch, pending read, cancellation and captured reader-closed receipts before releasing the reader lock, owned timer/listeners and lease. Idempotent `close()` permanently ends the budget and awaits the same settlement receipt. Clean close resolves even after an ordinary HTTP/read/cancellation failure. Unexpected cleanup failure permanently poisons the budget: the client preserves an existing read cause, or returns fixed internal `CleanupFailed` when none exists; close and later admissions fail with `CleanupFailed`. These internal errors add no public schema. Native transport settlement has local HTTP fixture coverage; arbitrary injected transports have no liveness guarantee.

The four single-request read adapters and the account method omit the budget. The internal collector consumes the owner’s original clock/start and leaves a successful budget open for final local inspection. The configured host now creates that single budget before initial SQL and holds its actual shared exclusion through final inspection, private proof assembly and awaited close. A final post-close fence uses the original owner freshness record; the permanently closed budget is never reopened.

The account envelope has numeric `code: 0` and all three required balance fields. Zod validates finite nonnegative numbers, strips unknown fields, and validates the public output with its observation timestamp. A task-list envelope must have `code: 0`, safe nonnegative integer page fields, and at most 1,000 task rows; its echoed page must match the request. Empty pages beyond `last_page` are allowed, while non-empty results beyond that inclusive final page are rejected. Every task has a nonblank opaque ID. Other documented summary fields are optional, validated when present, mapped to camelCase, and unknown fields are stripped. The public list output omits unavailable optional values.

Task status input uses one of six family values and exactly one ID form. Batch IDs must be unique and nonblank; the client uses unique IDs for exact correlation, and the provider documents a 1,000-ID maximum. A status response may contain one task or an array for either input form. The client validates known root and direct-child fields, strips unknown fields, maps names to camelCase, and correlates records by exact root ID. It returns tasks and omitted IDs in request order. `unreturnedIds` describes omissions in one response and does not establish that a task is missing. Optional fields remain omitted when absent. Counts and day values must be safe nonnegative integers; token charges and refunds must be finite nonnegative numbers. Status strings and explicit completion booleans pass through; the client does not infer completion from counts or status text. The optional `dripFeed` and `awaitingResult` flags are observed provider fields, not universal guarantees. Direct children carry common task/PPI fields and optional `day`, with no nested children.

If a known field on any returned task or direct child has the wrong type, the entire task-status call fails with no partial `tasks`; `unreturnedIds` reports omissions only from an otherwise valid response.

Task reports have a separate `src/task-report.ts` schema and normalizer. Generic report results require the documented core fields and preserve URL strings and array order exactly; optional known metadata is validated when present and unknown result-root fields are stripped. Provider IDs correlate exactly to the requested ID and appear publicly as `taskId` only. Backlink reports validate one page, its exact page/ID correlation, the requested donor limit, and opaque donor rows as finite JSON objects; nested donor keys and values are preserved. A wrong type or explicit `null` for a known field, or a donor row that is not an object, fails the whole call. Nested JSON null values inside valid donor objects remain allowed and are preserved. Empty pages beyond `lastPage` are valid, but nonempty pages beyond it are rejected. Report fields and counts do not establish completion, retry permission, or fresh Google indexing truth.

The four read tools return structured content and equivalent JSON text on success. Their errors use fixed messages without structured results, provider bodies or thrown error details. Each submission adapter validates its own structured success and error results, including identical JSON text; SDK 2.3.1 skips output validation for `isError: true`. SDK input validation occurs before the handler, so those input failures need not have application structured content.

The SDK stdio transport handles stdin EOF, closes the connection, and aborts in-flight requests. Startup and previews open no ledger. Enabled submits open existing V1/V2 state; configured retry planning opens existing V2 through query-only readers; only explicit local new-only V1/V2 commands create state. Offline migration is a separate exclusive local mode. CodeGraph is an optional developer tool, independent of the runtime and build. The executable starts no web listener, scheduler or deployment service.

## Guarded indexing submissions

`src/submission-contract.ts` defines pure submission scalar, unit and authorization schemas and coordinator DTOs. `src/create-indexing-task.ts` preserves the public indexing exports and owns strict indexing schemas, frozen provider bodies, quotes, fingerprints and root ACK normalization. `src/submission-policy.ts` loads an explicit bounded private JSON policy once and derives trusted key/UTC context. `src/submission-host.ts` uses one coordinator with trusted internal indexing, index-check and backlink-check strategies to connect that snapshot, the common V1/V2 ledger contract and a private paid transport. The read-only provider client has no submission method. The thin tool adapter forwards SDK cancellation and validates application output; it does not accept policy authority through MCP arguments.

Google submits always request Pay-Per-Result with explicit `drip_feed: false` or valid drip days. Yandex omits Google-only fields. The host serializes the validated body once, preserving title and ordered URL text, and hashes those exact UTF-8 bytes. It rejects overflow before preparation: 10,000 URLs, 8,192 bytes per URL, 1,024 bytes per title and 2,097,152 bytes per serialized body are inclusive limits. Google drip days are 2 to 30 and at most the URL count. Unsupported families, authority overrides, duplicate URLs and malformed Unicode fail validation without normalization or truncation. URLs are never fetched.

For N URLs, the independent maximum-exposure estimate is Google `100*N` tokens, or Yandex `20*N` tokens plus N indexer credits; checker exposure is zero. Yandex consumes credits first, so booking both independent maxima is conservative against outside credit use. The host does not read balances or net refunds against its reservation. Quote identity binds version, family, fixed route, exact body digest, URL count and three-unit exposure. It excludes key, policy and day so an unchanged payload keeps its quote across midnight.

The trusted policy has explicit enabled/mode/revision/scope/expected-key fields, finite safe-integer token/indexer/checker caps, and a UTC-day period kind. It may also contain the optional strict private `retry` object with exactly `enabled`, `allowUnattributedParents`, and positive safe-integer `maxAttemptsPerSource`. This field is a configuration prerequisite for public planning; it supplies no observations, original ancestry or paid retry authority. The loader requires a canonical absolute file, effective-UID ownership, mode `0600`, one hard link, no symlink, trusted ancestors and at most 16,384 bytes. It uses a no-follow descriptor with bounded reading and identity checks; it does not repair or discover files. The state path remains a syntactic reference until submit or configured planning. The trimmed visible-ASCII effective key is bounded at 8,192 bytes; its domain-separated SHA-256 must match the policy's expected fingerprint. A key fingerprint does not establish provider account identity. Raw keys, expected fingerprints and raw policy never enter tool results or logs.

The canonical policy digest includes caps and expected key but excludes the current day. The optional `retry` object is appended only when present, and all its values, including `false`, bind identity; omission preserves the prior digest exactly. Host clock time determines `utc-day:YYYY-MM-DD` and UTC midnight boundaries. Caller acknowledgement mode requires both current quote and authorization digests for a new intent; operator policy mode permits new submits without an acknowledgement, but validates both digests if supplied. The authorization digest binds quote, policy, key, scope and day. This echo detects stale context and supplies no human authentication, one-use permission or request-ID binding. Operators control host access and restart all cooperating hosts to apply policy changes; no reload loop exists. Incomplete/invalid configuration disables writes while preserving stdio/read availability.

The host performs these separate steps with no SQLite transaction spanning an await or network operation:

1. Validate and freeze the request. Return preview without key/state/network requirements. For submit, check trusted policy/key, operation permission, selected profile where required, context and cancellation, then open existing V1 or V2 state.
2. Read and compare an existing request ID for exact replay before the busy guard or current acknowledgement checks. Return durable state without another capability, reservation or POST. For new IDs, allow only one new in-flight submit per process, validate acknowledgement and prepare durably. Cross-process coordination uses the shared ledger.
3. Yield through a timer and an immediate to an actual I/O turn after prepare, allowing queued stdio cancellation. If cancelled, use the prepared version-zero CAS to cancel and release holds only after commit. A lost CAS requires a fresh read.
4. Claim once with the creator capability. Only the winning version-one claim receives an outcome token. Yield to another actual I/O turn, then perform final signal/body/header checks. A proven no-fetch failure after claim records rejected with a `not_sent` observation; V1 cannot cancel a dispatching intent.
5. Mark the attempt immediately before one HTTPS POST to `https://api.speedyindex.com` and the fixed engine `/v2/task/.../indexer/create` or `/checker/create` route. Send the frozen JSON, raw trimmed Authorization key, JSON Content-Type/Accept and package User-Agent. Reject redirects and use a 10,000 ms deadline through response-body reading. Do not retry, split, fall back or poll.
6. Read at most 65,536 response bytes before fatal UTF-8 and JSON decoding, independent of Content-Length. Record one accepted/rejected/unknown outcome even after caller cancellation, then close the ledger and release the guard.

Only HTTP 200 with root numeric `code: 0`, a valid opaque root `task_id` and exact root family establishes an accepted ACK. Optional PPR/drip echoes must match; omitted echoes are allowed. Local task-ID limits are 4,096 UTF-8 bytes, valid Unicode, nonblank and no C0/DEL controls, with accepted text preserved. Root codes 1 or 2 without any task-ID field on HTTP 200/401/402/413 establish rejection. Other post-invocation failures, including malformed/nested ACKs, redirects, resets, deadlines and aborts, remain unknown. The read tools retain their separate 16 MiB body limit.

A fully parsed valid ACK can record accepted despite a later abort. If outcome persistence fails, the host rereads once and returns only confirmed durable state. A held dispatching result separates the safe ACK observation as `recorded: false` with `OutcomePersistenceFailed`; an unavailable reread reports `StateUnavailable` with last-observed dispatching rather than asserting current durability. HTTP alone cannot return durable accepted success. Cancellation may suppress the SDK response while durable state remains the recovery reference.

## Index-check reservations and shared execution

`src/create-index-check.ts` owns the pure checker builder, quote union, public result validator and root ACK classifier. Its thin `tools/create-index-check.ts` adapter forwards SDK cancellation to the same `SubmissionHost` instance used by indexing. There is no public strategy selector, separate coordinator, per-tool busy flag or alternate endpoint authority. The pure shared contract module has no filesystem, state or network side effects; indexing exports and schema enums remain compatible.

Checker input selects Google, Yandex or Bing and preserves title/URL bytes under the common bounds. The frozen body contains only optional title and URLs. Quotes use `speedyindex-index-check-reservation-2026-10-21-v1`, basis `operator_configured_reservation`, `providerEnforced: false` and `providerFeesKnown: false`. An available quote binds the selected per-URL vector and its safe-integer product, family/route, exact body digest and count. An unavailable quote identifies unconfigured/invalid policy, missing profile or overflow and has no reservation or fingerprint. No balances are read. These local reservations are not provider prices, maxima, fees or predicted credit consumption; checker-credit conversion, priority and fallback remain unknown.

The private policy optionally accepts `allowIndexChecks` and a strict partial `indexCheckReservations` engine map. Permission requires explicit true as well as `enabled`; a profile alone grants nothing. Every present profile supplies all three explicit nonnegative safe integers. Compiled token floors dated 2026-10-21 are Google 3 and Yandex/Bing 2 per URL, based on the [technical FAQ](https://en.speedyindex.com/faq/#service-cost); these are local minimum admission values. Missing units, extra fields, nulls, unsafe values, or token amounts below the engine floor in any profile invalidate the whole policy. This blocks submissions through all three create tools until the policy is corrected and all cooperating hosts restart. Valid previews remain available; the checker reservation quote is unavailable for an invalid policy. The loader safely parses a policy once even with an incomplete state/key configuration, exposing only a frozen reservation source for preview. An active trusted policy owns the profile used by the host; a separate inactive preview source cannot override it. All cooperating hosts must restart after changes.

Absent extension fields preserve legacy canonical policy bytes. Present false/empty values and all selected or unselected profiles bind the whole policy digest. A changed profile can therefore conflict with an existing request ID even when the selected quote stays unchanged. It never releases or resets old holds. Available previews require no key or open state and prove no later write authority. Missing permission/profile and configuration/key/context/cancellation errors precede state access. After admission, exact replay precedes busy/new-intent acknowledgement, retains its original period, and needs no fresh acknowledgement across midnight. New work follows the common prepare/claim/two-I/O-turn/dispatch/record/reread path and shared three-unit caps.

Checker acceptance requires HTTP 200, root numeric zero, a bounded opaque task ID and exact checker family. Optional PPR/drip echoes may be absent or false; true, null or mistyped values, or any `drip_feed_days` field, are ambiguous. The same narrow rejection rules and held persistence/cancellation outcomes apply. A confirmed accepted durable read may omit an HTTP observation; any present accepted ACK must be recorded and match it. Real SDK cancellation after full receipt can suppress the caller's response while unknown state and all three selected units remain held; restart replay sends nothing and unresolved URLs block new indexing IDs too.

## Backlink targets and shared V1 execution

`src/create-backlink-check.ts` owns strict pure input, frozen serialization, reservation quoting, result validation and ACK classification. Its `tools/create-backlink-check.ts` adapter forwards arguments and `context.mcpReq.signal` to the same passed `SubmissionHost`. The private strategy invokes the existing coordinator, clock, transport and persistence path; it adds no per-tool guard, state schema or endpoint override.

Input requires explicit mode, 1 to 10,000 distinct donor URLs and 1 to 50 `targetDomains`. Each target is nonblank safe Unicode without C0/DEL controls, at most 8,192 UTF-8 bytes. Preserve exact case, spaces, order and duplicate targets without DNS parsing or normalization. Existing donor/title bounds apply, and the full UTF-8 body is at most 2 MiB. Body order is optional `title`, `urls`, `target_domains`; its digest binds the targets. The own strict request summary adds `targetDomainCount` structurally without widening either older schema. The only route is `/v2/task/backlink/checker/create` on the fixed production API host.

The optional private `allowBacklinkChecks` flag must be true as well as policy `enabled`. `backlinkCheckReservations` supplies every nonnegative safe-integer unit with tokens at least 2. The [official English API backlink section](https://en.speedyindex.com/api.php#backlink-create) documents 2 tokens per donor; the compiled 2026-10-21 floor is local admission, not a full fee or maximum. Indexer/checker credit use, conversion and target-count pricing effects remain unknown. Explicit zero in the other units is an operator reservation choice, not evidence of zero fees. There are no active/default profile values.

Quotes multiply the complete profile by donor count with exact safe BigInt arithmetic, without Cartesian expansion. They use `speedyindex-backlink-check-reservation-2026-10-21-v1` and a separate fingerprint domain, binding version, family, route, full-body digest, donor count, target count and both unit vectors in that order. Available/unavailable quotes retain the same fee-uncertainty flags as index checks; unavailable quotes omit vectors and fingerprints. Active configuration quotes only its admitted policy snapshot; an inactive key-free view cannot replace or supply its profile.

The canonical policy appends `allowBacklinkChecks` then `backlinkCheckReservations` after optional index-check fields, only when present. Both new keys absent preserve legacy bytes and V1 identity; present false or profile values bind the whole policy digest. Invalid flag/profile fields invalidate the whole policy even with backlink permission false, blocking all three create tools until corrected and all hosts restart. Configuration/key, separate permission, profile/overflow, context and cancellation gates precede state open; admitted exact replay precedes busy/current-ACK checks.

V1 stores only ordered exact donor URLs as holds plus the full payload digest, without raw target lists, target pairs or new core columns. An unresolved donor blocks new targets and other create families. Target changes under the same request ID conflict. Shared three-unit exposure, next-day replay, prepare/claim I/O yields, persistence/reread and cancellation boundaries remain unchanged. Backlink ACK acceptance requires root numeric zero on HTTP 200, an own safe opaque task ID and exact `backlink/checker`; optional PPR/drip fields follow conservative checker rules. Durable accepted acknowledges job creation, not completed analysis. A confirmed accepted read may omit a new observation; an unrecorded ACK can appear only in a held/error result. No scheduler, public retry/lineage workflow or automatic release is activated.

## Local V1/V2 ledger and limits

`src/submission-ledger.ts` records immutable request identity, exact submitted URL strings, three independent unit reservations, and prepared, dispatching and terminal outcomes. It stores no key, title, raw provider body, provider error or plaintext capability. The host supplies scope, period, caps, policy digests and quote data from trusted configuration; this repository chooses no operator values. For each credential and budget scope, period IDs and start times map one-to-one. A new reservation may reuse the latest mapping or create a period whose start is strictly later than every recorded start; aliases and earlier contexts fail with `StalePeriodContext`.

For an existing credential and request ID, replay comparison checks budget scope, policy revision and digest, task family and route, payload digest, quote version and fingerprint, reservation values, and the ordered exact URL strings. Period ID, period start and direct cap values are excluded from V1 replay identity; the host policy digest nevertheless binds cap changes to policy identity. An exact replay returns the stored intent and its original period without another reservation or current-period acknowledgement. Other immutable mismatches return `RequestIdConflict`. New reservations use trusted current caps; policy revisions do not reset retained exposure. Prepared/dispatching/unknown reservations count across all periods, and accepted reservations count for their original reservation day. Rejected/cancelled rows count zero. Exposure sums grow with retained history. Unresolved exact URL holds span scopes for that key; accepted rows release URL holds, allowing a deliberate new ID to submit again.

`initializeLedger` creates only a new private local directory and database. Initialize/open/maintenance entry points require a canonical absolute POSIX path. The parent of a new state directory must already exist, and each ancestor must be a non-symlink directory owned by root or the current UID and not writable by group or others; root-owned sticky temporary directories are permitted. The final state directory must be owned by the current UID with mode `0700`. The database and any sidecars must be regular files owned by the current UID with mode `0600`. Callers may resolve operating-system path aliases before calling; the module does not follow aliases.

A failed initialization may leave a directory, partial database or sidecars, or even a complete database of the selected version if a later validation fails. It does not automatically remove or retry that path. Inspect any artifacts before recovery and never replace state to bypass held reservations. Normal `openLedger` validates paths/files, opens without CREATE, verifies the complete V1 or V2 schema, then configures WAL/foreign keys/FULL/busy timeout. WAL configuration can change persistent journal mode and create sidecars after verification. SQLite opening and reads can also touch existing SHM bookkeeping before a wrong-version rejection; these bookkeeping effects are distinct from application bootstrap or repair. Open does not bootstrap, repair, reset, rebuild or replace records. Unresolved prepared/dispatching/unknown state stays held across reopen, without lease expiry, resend or automatic release.

Bun SQLite operations are synchronous. The 2,000 ms busy timeout controls lock waiting, not total latency; retained-history sums, inserts and other operations add work. SQL can block stdio parsing, reads, pings, cancellation delivery and timer callbacks. Verified pre- and post-claim I/O turns allow queued cancellation at those boundaries; they cannot interrupt SQL already running or atomically cancel a remote request. The HTTP 10-second deadline is not a whole-tool deadline. Actual SDK queued-cancellation tests cover both busy failure and successful prepare; a separate process test covers queued I/O after a winning claim.

SQLite transactions coordinate cooperating processes that open the same local database. They do not reserve SpeedyIndex wallet funds, identify an account, coordinate database copies or hosts, prevent other clients spending the same wallet, or guarantee that distinct submissions cannot create duplicate jobs. WAL with SQLite `synchronous=FULL` stays subject to the VFS, filesystem, storage hardware, and operating system; it is not a power-loss guarantee.

V1 records standalone intents without parent/campaign lineage. Explicit V2 initialization and offline migration add a singleton random ledger identity and one context per intent, with only two tables and two nonunique indexes. Migrated contexts remain `legacy_unattributed`; new ordinary preparations insert `standalone` in their existing transaction, while exact legacy/standalone replay never rewrites metadata. Normal open never migrates. Handles opened by this binary reject changed schema version or V2 ledger identity inside mutation transactions; this cannot control old binaries. All hosts must drain, stop and restart on the V2 binary for migration. See [state maintenance](state-maintenance.md) for exact commands, verified backup, uncertain receipts and manual recovery prohibitions.

The internal `readRetrySnapshot` opens existing complete V2 without CREATE, sets query-only before application queries and validates one coherent deferred read transaction. Its copied deeply frozen DTO contains scoped holds, unambiguous exact accepted manifests, joined all-state retry children, unresolved event/unit history, ambiguity and attribution gaps. The shared projection/revision helper also runs inside internal retry admission's writer transaction, using exact integer decimal text and stable ordered binding-selected rows across all budget scopes/families; it opens no second reader. Ownership digests enter private hashing only. Limits are technical completeness bounds, never new migration, ordinary-write or financial limits. Semantic read-only permits physical SQLite bookkeeping; unavailable never includes partial arrays/revisions.

`readRetryPlanningState` is a trusted internal read only. It returns the complete bounded snapshot plus period compatibility, per-unit cap decisions and a lifetime retry count from the same pinned query-only transaction. The count selects the exact key binding and parent family/ID across all scopes, policies, periods and states; replay adds no attempt. Usage includes current-period accepted reservations and all-period unresolved reservations in the selected scope, summed as exact decimal `BigInt` values. It never inserts a period. UTC checks run after SQL and again before return; synchronous reads provide no hard abort deadline. Holds remain complete across all families/scopes. These local decisions supply no provider finality, proof, external adoption or dispatch permission.

`readRetryReplay` shares the guarded existing-V2 boundary and strict schema/history/path/sidecar/identity/close checks. It compares the original full V1 replay identity and retry parent/manifest/plan context, returning only missing, conflict or durable replay state. Original policy identity is comparison data, never new-work authority. It requires neither today's revision/caps/holds/proof nor a full bounded snapshot projection, so historical exact replay survives projection limits. Ordinary/legacy IDs cannot acquire retry lineage. Both readers close before returning immutable results or fixed unavailable reasons; physical WAL/SHM bookkeeping remains possible. V1 requires explicit upgrade. The production owner below combines observation verification with these readers. Public planning uses these readers; retry submission and one-shot runtime activation remain separate work.

`openRetryLedgerV2` remains a separate local-only trusted internal factory, preserving the common host interface. New retry admission requires current complete selected-key revision, an unambiguous accepted local same-engine indexer parent, exact manifest and child URL subset; known own accepted retry children cannot be fresh parents. Unacknowledged dispatching/unknown retry contexts block new retry admission. Exact full retry replay precedes current revision/resource/budget/overlap gates and never creates another capability, event, reservation or lineage. Ordinary and retry request identities cannot be relabelled across modes. Existing period, independent three-unit caps and exact unresolved overlap rules remain unchanged.

V2 outcome association checks run inside the existing owner-token/CAS transaction: duplicate accepted references for a binding/family and retry self-parent ACKs fail without releasing dispatching holds or adding partial events. State and provider IDs are joined from core, never copied to a second ACK store. V1 duplicate ACK history is preserved. Local parent/revision correlation supplies no source finality, adoption, human approval or paid authority. These storage APIs activate no public retry dispatch, production parent adoption, one-shot orchestrator, automatic release or scheduler.

`composeVerifiedRetryAdmission` adds a separate internal storage boundary. Trusted host construction captures an immutable bound configuration, verifier methods and clocks; per-composition opaque references cannot be supplied as JSON authority. Collection closes guarded readers before awaiting the verifier, validates matching count-complete reports and exact safe URLs, and derives the normal regular indexing body, quote and context. If the caller signal is aborted when the verifier settles, collection returns `RetryCancelled`, including when the verifier rejects; collection exclusion lasts until that settlement. Earlier permission and validation checks retain their precedence, and an error name alone does not establish cancellation. Duplicate entries within each indexed or unindexed list collapse to their first occurrence, preserving order; `size` and `processedCount` must equal the combined unique-entry count, and URLs appearing in both lists are invalid. It permits local standalone manifests, explicitly permitted legacy manifests, or explicitly permitted external observed corpora; an external source adds only the real child and retry context, never invented parent rows, ACKs or fees. External manifest hashes use the distinct `speedyindex-provider-report-url-manifest-v1` domain; original manifest and wider ancestry remain unknown.

New preparation consumes its proof only after the existing `BEGIN IMMEDIATE` lock and exact historical replay check. It reprojects the complete local revision, checks current lifetime counts, period, independent caps and all-family/all-period exact holds, and checks monotonic expiry/regression and current UTC after the lock and immediately before insertion. Failed consumed proofs are not restored. Existing holds never expire with a proof. Current valid bound policies with absent/disabled retry permission still allow exact original replay, without another capability. Collection and an open writer mutually exclude each other within one composition. These checks preserve the existing core insertion, owner/CAS and ACK guards. The production host now shares its guard with the three create strategies; future public retry dispatch must use that owner and the existing one-POST/outcome rules.

The parent-first verifier constructor remains a controlled storage fixture path. The production constructor instead creates the same-key collector from immutable configuration and transport and encloses it with the existing local readers and private proof admission. Mixed construction is rejected; no caller callback supplies alleged observations, a pending proposal or minting authority. Report inputs are limited to 10,000 raw entries per report, proposals to 10,000 URLs, and safety evidence to 1–64 strict SHA256 digests. Before normalization, a separate cumulative 8 MiB raw URL meter sums the UTF-8 size of each JSON-serialized URL string plus one byte per entry across both reports’ indexed/unindexed lists and the eligible list; every repeated visit counts. The evidence byte count is the UTF-8 size of the JSON serialization of the original report pair, safety-evidence digest list and partition digest, with an 8 MiB limit. The normal serialized create body has an independent 2 MiB limit, and the sum of those evidence and body bytes must also stay within 8 MiB. These entry and byte bounds apply together. The byte ceilings cover those serialized components only; they do not measure total invocation memory or HTTP traffic. The pure internal `computeRetryPlanFingerprint` hashes an explicit public-safe tuple, excluding request IDs, observation time, raw key binding, ledger/path and ownership metadata while retaining opaque revision/policy/authorization/body/quote digests and source/safety/period identity. Pure comparison remains callable without collecting or minting a proof; comparison identity itself supplies no authority. Historical hashes cannot reconstruct discarded observations or provenance. Public `plan_retry` exposes comparison data through the bounded result contract below. Retry-submission tamper/replay validation, `submit_retry` and one-shot integration remain later gates.

## Public retry planning

`src/tools/plan-retry.ts` registers read-only `plan_retry` on the same host as all three create strategies. The strict input permits only optional `searchEngine: "google" | "yandex"` and defaults to Google. The adapter forwards the actual SDK signal to `SubmissionHost.planRetryToolResult` and returns its owned envelope unchanged. Extra authority fields fail SDK validation before the handler; there is no MCP path, key, policy, proof, request-ID or limit override. The configured owner requires matching enabled private configuration, enabled retry and complete existing V2 state. Construction/startup do not open it, and planning never initializes or migrates it.

`src/plan-retry-result.ts` owns a strict four-way public union and semantic consistency checks. Ready includes source/provenance, exact ordered eligible URLs and exclusions, counts, a regular indexing request/body digest, independent quote/exposure, configured authorization summary and canonical comparison preimage/fingerprint. Complete no_source invents no parent or quote. Blocked gives fixed blockers; incomplete reports retain the unknown count and either exact missing local URLs or null when their identity is unknown. Error uses fixed sanitized code/message and bounded read phase/cause enums, with no raw exception or provider body. Application `isError` is true exactly for error. SDK argument rejection remains a separate surface because it precedes application handling.

For structured result D, the complete application envelope E is `{content:[{type:"text",text:JSON.stringify(D)}],structuredContent:D,isError:D.status==="error"}`. The inclusive limit is `UTF8(JSON.stringify(E)) <= 2,097,152` bytes. It counts JSON escaping, the duplicated structured data and isError, rather than only D or the text. Overflow yields a fixed validated ResourceLimitExceeded envelope with no partial proposal. Construction, validation, freezing, hashing and serialization retain the original owner budget, provider/combined retention meters and final freshness/native-close fences. This application bound excludes SDK JSON-RPC framing/metadata and makes no process-RSS or hard whole-tool latency claim.

Public comparison commitments retain opaque policy/revision/authorization/body/quote identities while excluding credentials, raw credential bindings, private paths, ledger ownership/proofs, inspection labels and raw observations. A ready envelope grants no admission capability, approval or paid authority. It creates no job, reservation, retry/adoption row or parent history and issues only the collector's fixed read requests, without account/create calls. Query-only snapshots preserve complete logical SQL state; physical WAL/SHM bookkeeping can change. External observed corpora require captured private permission and retain unknown original ancestry. The two provider passes and selected-key local coverage cannot establish an atomic provider snapshot, provider-wide history or fresh indexing truth. `submit_retry` and one-shot execution remain unimplemented.

SDK cancellation aborts the real handler signal but may suppress its application reply. A rejected client promise therefore supplies no owner-completion receipt. The source cancellation fixture observes native peer termination, after_close and actual post-super owner settlement before a single good same-host recovery. This is source fixture/pre-header coverage; the real CLI has separate source/built ready/finite journeys, and pending-body settlement retains lower-layer native coverage. No test-only completion observer is part of the CLI or public API.

## Local retry history

Ordinal attempt-ref order has no chronological meaning. The comparison ref commits to private ledger/key/request identity without returning those preimages. The existing snapshot retains timestamps/reservations for prepared/dispatching/unknown attempts and ambiguous accepted references. Unambiguous accepted entries recover URL count from their manifest but retain null timestamps/reservation; rejected/cancelled entries also have null URL counts. History does not widen planner retention or reconstruct discarded details. It returns signed millisecond and reservation integers as decimal strings where available. Source attribution distinguishes standalone/legacy/retry local manifests from ambiguous or unattributed references; none establishes original ancestry or current provider truth. Public IDs remain exact; raw request IDs, URLs, private key/path/binding/ledger identity and proof/ownership material stay out of results.

The CLI loader requires explicit valid policy/state paths, an enabled policy and matching key; absent or disabled retry permission does not block history. Missing state yields `StateMissing` without creating a leaf, V1 yields `V2Required` without migration, and empty V2 yields honest `ok` with zero matching entries. A clean missing-state refusal permits explicit new-only V2 initialization after settlement and reuse of that same host. V1 migration still requires stopping all cooperating hosts and restarting them under the maintenance procedure. History does no HTTP, writer admission, source eligibility, paid cap/period evaluation, reservation or state repair. It remains separate from the planner's non-atomic two-pass provider observations and shared paid guard.

One original monotonic horizon begins before native SQL. No await spans a transaction or reopens a closed budget. Prebuilt fixed envelopes cover post-close failures without rebuilding success. ## Internal retry observations and comparison

`src/retry-observation.ts` captures a read client from trusted configuration and consumes a closed local snapshot and one caller-owned invocation budget. It reads all inclusive pages of Google regular, Google drip (`filter=drip_feed`, without a PPR subfilter), and Yandex regular, then all required root/child statuses. Missing-list local ACK references still require status. It reads the chosen source report and accepted direct retry-child reports whose status evidence is final or uncertain. Known unfinished children skip child-report reads and require complete active-manifest coverage. The collector reserves a complete fence and repeats the same ranges and work set once, including this fixed report set. Reports may fill absent safety fields; unsettled child finality or incomplete child evidence blocks planning as `PriorRetryEvidenceUnknown`. New, missing or changed safety facts stop the invocation. Matching passes remain non-atomic provider observations.

Exact family/ID reference sets bound roots at 2,000 and children at 4,000; discovering a child's role does not refund earlier root work. Every requested status-ID visit counts again toward 12,000. Status requests obey both 1,000 IDs and 65,536 serialized UTF-8 bytes, and opaque IDs retain the existing 4,096-byte safety bound. A narrow optional fourth report argument charges parsed indexed/unindexed array lengths before normalization: duplicates, invalid entries and repeated reports count toward 10,000 per report and 40,000 overall. Existing public report calls omit it.

`src/plan-retry.ts` validates the strict default-Google selector and requires coherent finality within a representable RFC3339 profile with validated calendar dates and offsets and seconds `00`–`59`. It requires greatest creation chronology and refuses older fallback past newer uncertainty or tied maxima. Valid RFC3339 leap-second timestamps block as `ConflictingEvidence` without older-source fallback. Provider drip children and known accepted own retry children cannot become original sources. Local reports must equal the durable manifest's exact unique union; missing and extra URLs block. External count-complete observed corpora need captured private permission, keep their provider-report manifest digest and retain unknown original ancestry. Exact exclusions combine all-family/all-period unresolved holds, complete cross-engine active manifests, scheduled drip coverage and indexed outcomes from complete final direct retry-child reports. An active external original with no proven full manifest blocks negative coverage.

The core builds a regular preview and existing independent quote for nonempty survivors. Versioned canonical safety, local and partition tuples plus the unchanged `computeRetryPlanFingerprint` produce comparison data, with no proof or admission capability. A final local planning view must match private ledger identity/revision and pass actual period, lifetime and all three cap decisions. The internal submission context retains the validated quote fingerprint; comparison refuses a different proposal quote as `SnapshotConflict` before building the identity. Correctly quote-bound policy and UTC-day changes remain comparison inputs. Public-safe preimages exclude keys, paths, ledger identity, ownership, request IDs, observation times, titles and fee fields. Their hashes cannot reconstruct discarded evidence.

Provider retention measures the actual whitelisted tuples, wrappers and simultaneous fence copies at 8 MiB. Combined retention measures UTF-8 JSON of local snapshots, provider facts, proposal, identity and retained/copied proof inputs at 24 MiB, counting repeated serialized occurrences. Neither bound measures RSS. The production owner checkpoints initial/final SQL, pure assessment/identity and safe-result serialization, then awaits native receipt settlement and budget.close.
