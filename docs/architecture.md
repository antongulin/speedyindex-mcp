# Architecture

The single package is a Bun stdio executable. `src/cli.ts` handles explicit help/version arguments and starts the SDK transport. `src/server.ts` creates the MCP server and registers `get_balance`, `list_tasks`, `get_task_status`, and `get_task_report` through their tool modules.

`src/client.ts` sends one GET per account or task-list call and one POST per task-status or task-report call. It builds routes from fixed endpoints and validated inputs. `list_tasks` reads one explicit zero-based page and never traverses pages automatically. `get_task_status` selects one fixed status route from six supported families and sends either one `task_id` or a `task_ids` array. `get_task_report` selects one fixed report route from six families and sends one opaque `task_id`; generic reports are unpaginated, while backlink reports send exactly one page with explicit page and limit values. Neither tool splits or retries requests, follows up, or requests another family. The injectable fetch function supports isolated tests; the production CLI provides no endpoint override. The raw API key goes only in the Authorization header. Redirects and automatic retries are disabled. A per-call abort controller enforces the 10-second deadline, combined with the SDK request cancellation signal. Timers are cleared after settlement.

The shared reader enforces this MCP's compiled-in 16 MiB ceiling on decoded response-body bytes before JSON decoding. This is a local safety bound, not a SpeedyIndex maximum or a hard process-RSS claim; unusually large pages and reports are rejected.

The account envelope has numeric `code: 0` and all three required balance fields. Zod validates finite nonnegative numbers, strips unknown fields, and validates the public output with its observation timestamp. A task-list envelope must have `code: 0`, safe nonnegative integer page fields, and at most 1,000 task rows; its echoed page must match the request. Empty pages beyond `last_page` are allowed, while non-empty results beyond that inclusive final page are rejected. Every task has a nonblank opaque ID. Other documented summary fields are optional, validated when present, mapped to camelCase, and unknown fields are stripped. The public list output omits unavailable optional values.

Task status input uses one of six family values and exactly one ID form. Batch IDs must be unique and nonblank; the client uses unique IDs for exact correlation, and the provider documents a 1,000-ID maximum. A status response may contain one task or an array for either input form. The client validates known root and direct-child fields, strips unknown fields, maps names to camelCase, and correlates records by exact root ID. It returns tasks and omitted IDs in request order. `unreturnedIds` describes omissions in one response and does not establish that a task is missing. Optional fields remain omitted when absent. Counts and day values must be safe nonnegative integers; token charges and refunds must be finite nonnegative numbers. Status strings and explicit completion booleans pass through; the client does not infer completion from counts or status text. The optional `dripFeed` and `awaitingResult` flags are observed provider fields, not universal guarantees. Direct children carry common task/PPI fields and optional `day`, with no nested children.

If a known field on any returned task or direct child has the wrong type, the entire task-status call fails with no partial `tasks`; `unreturnedIds` reports omissions only from an otherwise valid response.

Task reports have a separate `src/task-report.ts` schema and normalizer. Generic report results require the documented core fields and preserve URL strings and array order exactly; optional known metadata is validated when present and unknown result-root fields are stripped. Provider IDs correlate exactly to the requested ID and appear publicly as `taskId` only. Backlink reports validate one page, its exact page/ID correlation, the requested donor limit, and opaque donor rows as finite JSON objects; nested donor keys and values are preserved. Known wrong types and explicit `null` values fail the whole call. Empty pages beyond `lastPage` are valid, but nonempty pages beyond it are rejected. Report fields and counts do not establish completion, retry permission, or fresh Google indexing truth.

All four tools return structured content and equivalent JSON text. Errors use fixed messages without provider bodies or thrown error details.

The SDK stdio transport handles stdin EOF, closes the connection, and aborts in-flight requests. No web listener, database, scheduler, task submission, or deployment service is part of this package. CodeGraph is an optional developer tool, independent of the runtime and build.

The provider contract comes from the [official API reference](https://en.speedyindex.com/api.php) and the [account API page](https://app.speedyindex.com/cabinet/api). This integration is unofficial. Future tools need their own scope, action boundaries, documentation, and verification; see the [roadmap](implementation-plan.md).
